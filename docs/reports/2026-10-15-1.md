## Summary

The VM is serving Drupal 11 over HTTPS at https://ishoponamazonwaytoomuch.ohbah.com, hardened and patched automatically. Written up afterwards from NOTES.md and the session log.

## What was done

- **VM survey:** GCE `ishopwaytoomuch`, us-central1-a, e2-medium (2 vCPU, about 3.8 GiB RAM), Debian 13, 9.7 GB disk. Added a 2 GB swap file (swappiness 10).
- **Stack (approved by Liam):** Apache 2.4 with PHP-FPM 8.4, MariaDB 11.8 (listens on 127.0.0.1 only; its own database and user), Drupal 11.4.10, Drush 13. PHP limits: 256 MB web, 512 MB CLI, 32 MB uploads, OPcache and APCu.
- **Project:** /var/www/ishop, web root `web/`, private files and secrets outside it. Database credentials and the hash salt live in `secrets/`, which git ignores. Local git repo, baseline commit 2ee9e25.
- **DNS and HTTPS:** FreeDNS A record for the subdomain. Let's Encrypt certificate, HTTP to HTTPS redirect, `certbot.timer` renewal with a successful dry run. HSTS for one day only, without subdomains, because ohbah.com is shared. The bare IP redirects to the domain.
- **Hardening:**
  - Unattended upgrades, with reboots about 4 a.m. Pacific (server time zone America/Los_Angeles).
  - nftables firewall that drops all incoming traffic except SSH, HTTP, HTTPS and the basics.
  - fail2ban on SSH, aggressive mode, ignoring Google's IAP and SSH-in-browser ranges.
  - LLMNR and mDNS off; Apache ServerTokens Prod and TraceEnable Off.
- **Accounts:** webmaster (Liam; he set the password himself through a one-time link), site-foreman (the agent; no password, Drush only), theowner (Cody, full administrator).

### Incident

The Drupal installer appended a database settings block to settings.php, and the database password appeared once in the agent's session output. It was not written anywhere else. The block was removed and the database password was changed the same morning, so the exposed value no longer works.
